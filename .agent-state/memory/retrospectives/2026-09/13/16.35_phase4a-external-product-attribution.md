## AI Diary

I began this session with a plausible but overly tidy causal story: several failures looked like
compaction problems, and one checkpoint visibly contradicted the repository. That story became less
comfortable once the fresh verifier reconstructed the earlier turns. The typography mistake was
already present in reviewer and model reasoning before the checkpoint; the checkpoint propagated
the mistake but did not create it. The commit incident was also more ambiguous than I had reported,
because the model itself bundled memory approval and a Git commit in one question. I had flattened
that nuance into “no textual grant,” which was wrong. Correcting those claims made the report less
dramatic but much more useful.

I also repeated a familiar documentation mistake at the end: I tried to make the evidence
discoverable by inserting a dated case-study summary into the product README. Mahiro immediately
recognized that it did not belong there. Discoverability is not automatically relevance, and a
public product surface should not become a feed of internal investigation milestones. His second
correction about proprietary external-project identifiers exposed the same underlying issue from a
privacy and ownership angle. I fixed both surfaces and verified zero prohibited occurrences before
continuing. The strongest lesson for me is that evidence can be worth preserving without being
promoted into every current owner. I need to choose the narrowest legitimate home, not maximize the
number of links to the work.

## Honest Feedback

Three friction points mattered. First, the initial report used numeric causal confidence before the
counterevidence was mature. Numbers made weak attribution look more scientific than it was; the
qualitative Strong/Mixed labels are more honest for retrospective traces. Second, I initially
treated a screenshot critique where Mahiro selected one of five suggestions as a reliability
failure. That was ordinary collaborative iteration, and conflating it with false-ready behavior
would make the system look worse while reducing the report's precision. Third, I let the desire for
documentation completeness override documentation ownership. The README addition was unrelated to
the product's user-facing job, and the first report name leaked an external project identity into a
repository that should remain universal. The correction loop was efficient once Mahiro pointed it
out, but both misses were preventable with a pre-write owner question: “Does this text describe the
current product, or only the investigation?” I should apply that check before touching public or
always-active documentation.

## Lessons Learned

- Inspect effective context before attributing a failure to compaction; a checkpoint can preserve an
  earlier bad decision rather than originate it.
- A combined approval question is itself a gate-design defect when the actions have different
  authority boundaries.
- Reviewer freshness does not prove claim relevance; the reviewer must attack the material product
  claim and its current consumer.
- Keep external case studies neutral and scoped. Public/current product docs should change only when
  current product truth changed.
- A dated supporting report can remain useful without being promoted into the README.
