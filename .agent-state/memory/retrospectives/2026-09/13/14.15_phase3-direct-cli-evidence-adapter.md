## AI Diary

I began this work with too much confidence in a repository-owned host adapter. The important correction was realizing that the installed Direct CLI workflow already owned the difficult runtime boundary: creating and identifying the pane, preserving the Agy session, dispatching the prompt, delivering the callback, acknowledging it, and cleaning up. Continuing to model those responsibilities inside this repository would have produced two competing truths and made the evidence harder, not safer, to reason about. Once Mahiro corrected the ownership boundary, the implementation became smaller in responsibility even though its validation remained substantial.

The independent review was the most valuable part of the session. My first “ready” assessment accepted a caller-selected live mode and projected Phase 2 events as though they were native runtime observations. That was a real false-PASS risk. I also allowed documentation to describe a self-hash using signing language, which overstated its security property. I responded by changing the data model rather than defending the implementation: fixture and live provenance now come from distinct schemas, compatibility evidence is named as compatibility evidence everywhere it survives, provider actions are not invented, and replay checks MemFS as well as repository state. The resulting claim is narrower but far more trustworthy. I am satisfied that the final state says exactly what was proven and no more.

## Honest Feedback

1. **Ownership discovery came too late.** The early path spent meaningful time designing transport behavior that Direct CLI already owned. A pre-write owner map against the installed runtime contract should have happened before implementation, not after architectural pressure exposed the duplication.
2. **The first closeout was too optimistic.** Passing tests and a successful canary did not prove that the evidence semantics were truthful. The independent verifier correctly found that a self-consistent adapter can still launder fixture input or synthetic compatibility events into stronger claims. Future evidence work needs provenance and nonclaim review before readiness language.
3. **Goal and evidence administration was heavier than the code correction.** Recording each criterion and plan transition accurately was useful, but the sequence was verbose and easy to make stale. The process should continue using exact evidence IDs while avoiding premature records that must later be superseded after final-source changes.

## Lessons Learned

- Runtime ownership must be established before an evidence adapter is designed; adapters verify completed native receipts and must not quietly become alternate runtimes.
- Provenance cannot be a caller preference. Distinct runtime-owned schemas must determine whether evidence is live or fixture.
- Compatibility projections are acceptable only when visibly labeled in the stream, checkpoint, documentation, and every retained standalone report.
- Hash binding proves cooperative-local consistency, not cryptographic authenticity or hostile same-UID rewrite resistance.
- Independent verification should attack the meaning of evidence, not merely repeat tests or confirm parser consistency.
